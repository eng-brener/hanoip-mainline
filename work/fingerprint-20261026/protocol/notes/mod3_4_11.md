# Protocolo dos modulos 3 (hw_auth), 4 (db_blob) e 11 (bio) — TA FPC do Moto G60

Análise **estática e offline** de:

- TA: `work/fingerprint-20261026/fpctzapp-reconstructed.elf` (ELF32 ARM LE, Thumb, VMAs desde 0)
- HAL: `work/fingerprint-20261026/android-live-readonly/programs/fingerprint-service-fpc` (ELF64 AArch64)
- símbolos: `ta-dynamic-symbols.json` / `hal-protocol/fingerprint-service-fpc-symbols.json`
- desmontador: `llvm-objdump --triple=thumbv7 | --triple=aarch64`

Nada foi executado, nada foi enviado ao aparelho. Ferramentas novas em `protocol/tools/`
(`ann.py` desmonta faixas e anota `bl`/`b`/`bx` com os nomes exportados; `scan_frames.py`
lista todos os frames `{module_id, cmd_id}` que o HAL monta, por função).

Legenda de rigor: **[O]** observado (instrução citada prova), **[I]** inferido,
**[?]** desconhecido.

## 0. Correção importante do frame (antes de tudo)

O briefing dizia “`+0x14` = limite de resposta na entrada; payload em `+0x18`”.
**Não é o que este TA/HAL fazem.** O que as instruções provam:

| off | tipo | significado | prova |
|-----|------|-------------|-------|
| `+0x00` | u32 | `module_id` | `0x1d8 ldr.w lr,[r12]` (roteador 0x1a8) |
| `+0x04` | u32 | `cmd_id` | `0x1fe ldr.w r2,[r12,#4]` |
| `+0x08` | u32 | tamanho/valor (in **e** out) | `0x214 ldr.w r4,[r12,#8]`, `0x98e str.w r0,[r9,#8]` (mód. 11) |
| `+0x0c` | — | **payload** (a resposta sobrescreve o mesmo buffer) | `0x21a add.w r5,r4,#0xc` + `0x21e cmp r5,r1`; `0x414a add.w r0,r6,#0xc` (mód. 4) |

O “limite de resposta” **não é campo do frame**: é o argumento `r1` (tamanho do buffer
compartilhado) que o TEE entrega ao roteador → `bx r3` em `0x23c` chama
`handler(frame, buflen, cmd)`. Os handlers comparam `chunk + 0xc <= buflen`
(`0x411e-0x4124` no módulo 4).

**Transporte [O].** O QSEECom sbuffer tem 128 bytes (req 64 + resp 64):
`0x22b08 mov w8,#0x80` / `0x22b20 QSEECom_start_app(...,w3=0x80)`;
`0x22e14 mov w2,#0x40` e `0x22e24 mov w4,#0x40` em `QSEECom_send_modified_cmd`.
O frame real vive num **buffer ION separado**, entregue por fd
(`0x22e38 ldr w9,[x1,#0x10]` + `0x22e40 stp w9,w10(=4),[sp,#8]` → `fd_info={share_fd,4}`).
Por isso 1,7 MB de banco de digitais atravessa sem caber em 64 bytes.

## 1. Módulo 3 — `hw_auth` (handler `0x3da4`, entrada na tabela `0x11608c`)

Despacho: `0x3dce tbb [pc,r0]` com `r0 = cmd-1`, tabela em **0x3dd2**, só `cmd 1..6`
(`0x3dca cmp r0,#5; 0x3dcc bhi`). Pré-condições: `frame != 0` (`0x3db8`) e
`buflen >= 0x10` (`0x3dc2`).

| cmd | handler | nome (fonte) | req | resp |
|-----|---------|--------------|-----|------|
| 1 | `0x3dd8` | `set_auth_challenge` (HAL 3/1) | `+8` u64 | — |
| 2 | `0x3df6` | `get_enrol_challenge` (HAL 3/2) | — | `+8` u64 aleatório |
| 3 | `0x3e2e` | `authorize_enrol` (HAL 3/3 via `movi`) | `+8` u32 ≥ 0x45, `+0xc` u8[0x45] | — |
| 4 | `0x3e3a` | `get_auth_result` (HAL 3/4) | `+8` u32 ≥ 0x45 | `+0xc` token de 0x45 bytes |
| 5 | `0x3e46` | `init_hw_auth` / unwrap (HAL 3/5) | `+8` u32 len, `+0xc` blob | — |
| 6 | `0x3e74` | `set_token_validation_enable` | `+8` u8 | **não implementado** |

Contexto do módulo em **0x2ce1f0** (.bss, zerado no arquivo; resolvido por três caminhos
independentes: `0x3dde`, `0x3e9a`, `0x3eb6`):

```
+0x00 u32   ponteiro p/ S (S+0x00 = banco, S+0xa8 = resultado de match, 0x2c bytes)
+0x08 u8[8] challenge do host (cmd 1)            +0x10 u8[8] challenge do TA (cmd 2)
+0x18 u64   uptime do challenge (cmd 2)          +0x20 u8[0x45] token recebido (cmd 3)
+0x65 u8[32] chave AES (cmd 5)                   +0x88 u32 flag "chave instalada"
```

`0x20 + 0x45 = 0x65` encaixa exatamente antes da chave — indício forte de que o
layout acima está certo.

### cmd 1 — `set_auth_challenge`
```
0x3dda  ldrd r4,r6,[r4,#8]        ; lê 8 bytes do frame em +8      [req +0x08]
0x3de2  adds r0,#0xa8             ; r0 = S+0xa8
0x3de4  bl 0x3c0                  ; fpc_match_result_reset
0x3de8  strd r4,r6,[r5,#8]        ; ctx+0x08 = challenge
0x3dec  movs r0,#0                ; retorna 0
```
HAL: `0x208a0 str x19,[x8,#8]` (64 bits).

### cmd 2 — `get_enrol_challenge`
```
0x3dfc  str r0,[r4,#8]!  / 0x3e02 str r0,[r4,#4]   ; zera frame+8 e +0xc
0x3e0a  movs r1,#8  / 0x3e0c bl 0x393c             ; fpc_secure_random(frame+8, 8)
0x3e10  ldrd r1,r2,[r4] / orrs / bne 0x3e78        ; repete (até 6x) se veio zero
0x3e82  strd r0,r1,[r5,#24]                        ; ctx+0x18 = fpc_get_uptime()
0x3e8a  strd r0,r1,[r5,#16]                        ; ctx+0x10 = 8 bytes sorteados
```
HAL: `0x2090c ldr x8,[x21,#8]` (lê 64 bits de `+8`). Se `fpc_secure_random` devolver
zero 6 vezes seguidas: `0x3e1e movw r1,#0x40ac` + `0x3e24 movt r1,#0xe853` → `0xe85340ac`.

### cmd 3 — `authorize_enrol` (validação do token)
```
0x3e30  cmp r0,#0x45 / 0x3e32 bhs        ; exige +0x08 >= 0x45 (senão 0xe8a340bc)
0x3e94  add.w r1,r4,#0xc                 ; origem = payload
0x3e98  movs r2,#0x45
0x3e9a  add r0,pc / 0x3e9c adds r0,#0x20 ; destino = ctx+0x20
0x3e9e  bl 0x52ba                        ; memcpy (sem símbolo)
0x3eac  b.w 0x3cb0                       ; tail-call p/ a validação (sem símbolo)
```
Dentro de `0x3cb0` (nomes das strings/códigos conforme o dump):
```
0x3cc6  ldr.w r1,[r8,#0x88] / cbz       ; exige chave instalada (0xe913406f)
0x3ccc  ldrd r1,r2,[r8,#16]             ; ctx+0x10 vs bytes 1..8 do bloco (0xe8a34079)
0x3d16  movw r2,#0x27c1 / movt r2,#9    ; 0x927c1 = 600001 ms ≈ 10 min de validade
0x3d28  blo 0x3d4c -> add r0,r8,#0x20 -> 0x3c00 fpc_check_token_integrity(ctx+0x20)
0x3d2a  expirado: 0xe8c34083 e zera ctx+0x10..0x17 (strd r1,r1,[r8,#16], r1=0)
```
`fpc_check_token_integrity` (`0x3c00`): `0x3c10 ldrb r0,[r4]` + `cmp r0,#0` (versão 0),
`0x3c30 movs r1,#0x25` + `0x3c32 movs r3,#0x20` + `0x3c34 bl fpc_hmac_sha256`
(HMAC sobre os 37 primeiros bytes, chave `ctx+0x65`) e `0x3c44 fpc_crypto_memcmp` com
`r4+0x25` (erro `0xe8a34055`).

**Consequência [I]:** o token só valida se `ctx+0x08` (enviado no cmd 1) for **igual** a
`ctx+0x10` (sorteado no cmd 2) — ou seja, o host deve chamar `set_auth_challenge` com o
valor devolvido por `get_enrol_challenge`.

### cmd 4 — `get_auth_result` (produz o token de 0x45 bytes)
```
0x3e3c  cmp r0,#0x45 / 0x3e3e bhs          ; +0x08 = capacidade do host, >= 0x45
0x3ec4  bl fpc_db_get_index_of_id32        ; id32 guardado em S+0xb0
0x3ed8  bl fpc_db_get_secure_user_id       ; 8 B -> sp+0x18
0x3ee2  bl fpc_db_get_database_id          ; 8 B -> sp+0x08
0x3ef0  ldrd r0,r1,[r0,#168] (=S+0xa8) + 0x3ef4 bl fpc_htobe64
0x3efa  movs r0,#2 + 0x3efe bl fpc_htobe32
0x3fe0  mov r0,r8      ; r8 = frame+0xc (setado em 0x3eec add.w r8,r4,#0xc)
0x3fe2  movs r1,#0x25  ; 37 bytes de cabeçalho
0x3fe4  bl fpc_hmac_sha256   ; r2 = ctx+0x65, r3 = 0x20, out = frame+0x31
```
Layout resultante (offsets no **frame**, e relativos ao bloco):

| frame | bloco | tipo | conteúdo | prova |
|-------|-------|------|----------|-------|
| `+0x0c` | 0x00 | u8 | versão = 0 | `0x3f08 strb r1,[r4,#0xc]` |
| `+0x0d` | 0x01 | u64 | cópia crua de `ctx+0x08` (challenge) | `0x3faa ldrd r0,r1,[r6,#8]`, `0x3fc6-0x3fd8` |
| `+0x15` | 0x09 | u64 | `secure_user_id` | `0x3f24-0x3f30` / `0x3f10-0x3f1e` |
| `+0x1d` | 0x11 | u64 | `database_id` | `0x3f52-0x3f60` / `0x3f3c-0x3f4a` |
| `+0x25` | 0x19 | u32 **BE** | valor `2` | `0x3efa movs r0,#2` + `htobe32`; bytes `00 00 00 02` |
| `+0x29` | 0x1d | u64 **BE** | `*(u64*)(S+0xa8)` | `0x3ef4 fpc_htobe64` + `0x3f74-0x3fa2` |
| `+0x31` | 0x25 | u8[32] | HMAC-SHA256 do bloco | `0x3fe4` |

O byte de versão e os três `u64` seguintes são **cópias cruas** (o TA só copia bytes);
apenas os dois últimos campos do cabeçalho (bloco `0x19` e `0x1d`) saem em **big-endian**.

### cmd 5 — `init_hw_auth` (unwrap da chave)
```
0x3e48  movs r0,#0x20 / 0x3e50 str r0,[sp,#0x18]   ; capacidade de saída = 32
0x3e4a  ldr r1,[r4,#8]                             ; tamanho do blob (+0x08)
0x3e54  str.w r0,[r5,#0x88]  (r0=0)                ; limpa a flag antes
0x3e58  add.w r0,r4,#0xc                           ; entrada = payload (+0x0c)
0x3e5c  add.w r2,r5,#0x65                          ; saída = ctx+0x65
0x3e60  bl fpc_ta_hw_auth_unwrap_key
0x3e6c  str.w r0,[r5,#0x88]  (r0=1)                ; sucesso -> flag
```
`fpc_ta_hw_auth_unwrap_key` (`0x4004`): `0x4016 blx 0xcc` → **veneer ARM** para a tabela de
syscalls do TEE (fora da imagem); depois `0x4026-0x4030` comparam o rótulo com
**`"keymaster64"`** (literal `0x7c3d7`, base `0x4032` → string em `0x80409`), senão
`0xe8a3802c`. Ou seja: **a chave vem do keymaster**, não é derivada de senha.

### cmd 6 — não implementado
```
0x3e74  mov r0,r3        ; r3 = 0xe8a34063 (carregado em 0x3dae/0x3db4)
```
Retorna sempre o código base de erro (o mesmo usado quando `frame == NULL`).
O HAL (`0x20ab4`) envia `1` byte em `+8` e apenas registra o status no log (`0xb4e4`).

## 2. Módulo 4 — `db_blob` (handler `0x4048`, tabela `0x11609c`)

Despacho: `0x4084 tbb [pc,r1]` com `r1 = cmd-6`, tabela em **0x4088**; só `cmd 6..17`
(`0x4078 cmp r1,#0xb; 0x407a bhi`). Pré-condições: `buflen >= 0x70` (`0x406e`) para
todos, `frame != 0`.

| cmd | handler | função | estado exigido |
|-----|---------|--------|----------------|
| 6 | `0x4094` | tamanho do blob | — |
| 7..13 | `0x4108` | default/erro | — |
| 14 | `0x40b0` | abre a transferência (modo 0 = leitura, 1 = escrita) | `ctx+0x00 == -1` |
| 15 | `0x4100` | reset / fecha (limpa o buffer) | — |
| 16 | `0x4112` | lê chunk (TA → host) | `ctx+0x00 == 0` |
| 17 | `0x416c` | escreve chunk (host → TA) + commit no último | `ctx+0x00 == 1` |

Contexto em **0x1160ac** (variável global **inicializada**: no arquivo vale `0xffffffff`
com zeros até `0x1160bb` — prova de que nasce em estado `-1` e ocupa 0x14 bytes):

```
+0x00 u32 estado (-1 ocioso | 0 leitura | 1 escrita)
+0x04 u32 tamanho do blob     +0x08 u32 restantes
+0x0c u32 offset              +0x10 u32 ponteiro do buffer (= global+0xdc)
```

### Formato do blob [O]
```
fpc_get_wrapped_size(0x3984):  adds r0,#0x34        -> overhead fixo de 52 bytes
fpc_wrap_crypto(0x3988):       str r9,[r5]          -> [0] = tamanho plano
                              memcpy(out+0x34, in, len)   (0x39b8)
                              veneers 0x90/0x9c preenchem o cabeçalho de 0x34 B
fpc_unwrap_crypto(0x3a04):     ldr r0,[r5] / len+0x34 <= in_len (0x3a28-0x3a2e)
                              devolve ponteiro p/ in+0x34 ou copia
```
→ `{u32 tamanho_plano @0, cabeçalho 0x34 B, ciphertext @0x34}`. O algoritmo é
**[?]** (veneer → TEE).

### Tamanho máximo [O]
`0x40c4 movw r5,#0x57ff` + `0x40ca movt r5,#0x1b` → `0x1b57ff`; `0x40d0 cmp r0,r5`
valida `tamanho-1`; `0x4262 adds r2,r5,#1` valida o empacotado `<= 0x1b5800`.
Esse é exatamente o tamanho dos dois buffers alocados no módulo 11 cmd 0
(`0xa04 movw r8,#0x5800` + `0xa0a movt r8,#0x1b` → `global+0xdc` e `global+0xe0`).

### Comandos

**cmd 6 — tamanho** (`0x4094`): `fpc_db_get_data_size` (`0x409a`) →
`fpc_get_wrapped_size` (`0x40a8`) → `0x40ac str r0,[r6,#8]`. Resposta: `+0x08` u32.
O HAL zera `+8`, chama e lê o tamanho (`0x20c08`/`0x20c18`).

**cmd 14 — abrir**
```
0x40b4  ldrd r2,r1,[r6,#12]     ; r2 = +0x0c (modo), r1 = +0x10 (tamanho)
0x40be  ldr r3,[r4] / adds r3,#1 / bne erro   ; exige estado -1
0x40d8  cmp r2,#0  -> modo 0 = 0x4234
0x40e2  cmp r2,#1  -> modo 1 = 0x40e8 ; senão erro 0xe890c07e
```
- modo 1 (host vai **escrever**): `0x40e8 ldr.w r0,[r9,#0xdc]` / `0x40ec str r0,[r4,#0x10]`
  (buffer) / `0x40f6 strd r0,r1,[r4]` (estado=1, total) /
  `0x40fa strd r1,r10,[r4,#8]` (restantes=total, offset=0).
  HAL: `0x21118 stp w9(=1),w23,[x8,#0xc]`.
- modo 0 (host vai **ler**): `0x4238 str r0,[r4]` (estado=0) → `fpc_db_get_data_size`
  → valida limite → `0x4258 fpc_get_wrapped_size` → `0x425c str r0,[r4,#4]` →
  `0x4260 str r1,[r4,#0xc]` (offset 0) → `0x426e str r1,[r4,#0x10]` (buffer) →
  `0x427c fpc_db_get_data` (copia o banco p/ `global+0xe0`) →
  `0x428e fpc_wrap_crypto` → `0x42a8 streq r0,[r4,#8]` (restantes=empacotado) →
  `0x42b4 fpc_memset_s` (limpa o texto plano). HAL: `0x20c34 stp wzr,w23,[x8,#0xc]`.

**cmd 15 — reset** (`0x4100` → `0x42f8`): `0x4300 ldr r0,[r4,#0x10]` + `0x4308 fpc_memset_s`
limpa o buffer; `0x4312 vst1.32` zera `ctx+0x04..0x13`; `0x4316-0x431a` voltam o estado a `-1`.

**cmd 16 — leitura de chunk (TA → host)**
```
0x4112  ldr.w r8,[r6,#8]                 ; chunk pedido (+0x08)
0x411a  add.w r1,r8,#0xc / cmp r1,r5 / bhi erro   ; chunk+0xc <= buflen
0x413c  cmp r1,#0 / bne erro             ; estado tem de ser 0
0x4140  ldr r5,[r4,#8] / cbz erro        ; restantes
0x4146  ldrd r1,r2,[r4,#12]              ; offset, buffer
0x414a  add.w r0,r6,#0xc                 ; destino = payload +0x0c
0x4152  movlo r8,r5                      ; chunk = min(pedido, restante)
0x4154  add r1,r1,r2 / 0x4158 bl 0x52ba  ; memcpy(payload, buffer+offset, chunk)
0x415c  sub.w r10,r5,r8                  ; RETORNO = restantes
```
O retorno da **função** (não do frame) é “bytes restantes”; `0` = fim.
HAL compara com o esperado e loga `REE and TEE out of sync (%u vs %d)`
(`0x20cbc-0x20cc4`, string `0xdfaa`).

**cmd 17 — escrita de chunk (host → TA) + commit**
```
0x4196  cmp r1,#1 / bne erro             ; estado tem de ser 1
0x41a0  ldrd r2,r3,[r4,#12]              ; offset, buffer
0x41a4  add.w r1,r6,#0xc                 ; origem = payload
0x41ae  adds r0,r3,r2 / 0x41b2 memcpy    ; buffer+offset <- payload
0x41b8  subs.w r10,r0,r8                 ; restantes
0x41c6  bne 0x4108                       ; só no último chunk faz o commit
0x41cc  ldr r1,[r4,#4] (total) / 0x41d6 fpc_unwrap_crypto(buf,total,&sp+4,&sp+8)
0x41e4  fpc_db_destroy / 0x41ee fpc_db_create(db,[sp+4],[sp+8])
0x4214  memcmp 8 B: db+0x14 vs handle+0x10  -> 0xe920c0f8 se divergir
```

### Fluxo do blob no host (o que o HAL faz com o arquivo) [O]

**store_template_db_host** (`0x20ae0`) + **fpc_write_db_blob_to_file** (`0x20f40`):
1. `mkdir(dirname(path), 0700)` (`0x20b6c`); tamanho antes via `stat`.
2. **cmd 6** (`+8`=0) → tamanho empacotado.
3. **cmd 14 modo 0** (`+0xc`=0, `+0x10`=tamanho) → TA empacota no buffer interno.
4. `malloc(tamanho)` + `fpc_tac_alloc_shared(min(tam,0xffff90)+0x70)`.
5. Laço **cmd 16**: `+8` = `min(tam,0xffff90)`, payload em `+0xc`; retorno = restantes;
   `memcpy(malloc+n, payload, chunk)` até retornar 0.
6. `fpc_write_db_blob_to_file`: `open(O_WRONLY|O_CREAT|O_TRUNC=0x241, 0600)`
   (`0x20f5c-0x20f68`), `write`, `fsync`, `close`, confere bytes (`0x20fa8`).
7. **cmd 15** (reset) em `0x20e34`.

**load_template_db_host** (`0x21060`) — contém o `fpc_read_db_blob_from_file` inlinado
(a string `0xc42d` existe, o símbolo não):
1. `stat`; se não existe (`errno==2`) → **cmd 11/7** (`load_empty_db`).
2. **cmd 14 modo 1** (`+0xc`=1, `+0x10`=tamanho) em `0x21100-0x21124`.
3. `open(O_RDONLY)` + `read(tamanho)`; leitura parcial → erro `0x980d`.
4. `alloc_shared(min(tam,0xffff90)+0x70)`; laço **cmd 17** (`memcpy(payload, buf+n, chunk)`).
5. **cmd 15** em `0x213c4`.
6. Se o TA recusar o blob (erro `-18`), `remove(path)` (`0x21374`) e recarrega banco
   vazio (`0x2137c`).

Teto do chunk no HAL: `0xffff90` (`0x20c54`/`0x20c58`), que é maior que qualquer blob
possível — na prática o TA sempre limita por `restantes`.

## 3. Módulo 11 — `bio` (handler `0x420`, tabela `0x116030`)

Despacho: `0x472 tbh [pc,r2,lsl #1]`, tabela de meias-palavras em **0x476**, `cmd 0..11`
(`0x452 cmp r2,#0xb; 0x456 bhi 0x98c`). Pré-condições: `buflen >= 0x70` (`0x440`).
Epílogo `0x98c-0x98e`: `ldr r0,[sp,#0x14]` + `str.w r0,[r9,#8]` → **`+0x08` é o campo
in/out de tamanho/valor da resposta**.

| cmd | handler | função (HAL) | req | resp (`+0x08` etc.) |
|-----|---------|--------------|-----|----------------------|
| 0 | `0x48e` | `bio_init` | — | — |
| 1 | `0x4e0` | `begin_enrol` | — | — |

Contexto: o código carrega um **ponteiro** do slot `0x2cf07c` (`0x498 ldr r5,[r6]`; no arquivo
vale `0x001188d8`) e usa offsets a partir do objeto. Campos relevantes [O]: `+0x00` handle
interno do banco (é ele, não o objeto, que vai como 1º argumento de `fpc_db_*` — `0x68c
ldr r0,[r5],#116`), `+0x04` gid, `+0x08` estrutura de resultado do identify (0x44 bytes,
`0x6e4 memset(ctx+8,0,0x44)`, `+0x08` = flag de match), `+0x4c`/`+0x50` lidos como
quality/coverage, `+0x60` status do enrol, `+0x70` amostras restantes, `+0x74` array de
templates (passos de 8 bytes), `+0x9c` = máx. de templates **fixo em 5**, `+0xd8` instância
do algoritmo, `+0xdc`/`+0xe0` buffers de `0x1b5800` B. O buffer da **imagem** não está aí:
vem de `fpc_common_get_handle()+0x08` (`0x570`/`0x6b2 ldr r1,[r4,#8]`).

### `identify` (cmd 4) — detalhe
```
0x662  add.w r0,r9,#0xc / 0x674 vst1.32  ; zera frame+0x0c..0x20

0x722  [ctx+0x50] -> [frame+0x0c]      0x728 [ctx+0x4c] -> [frame+0x10]
0x72e  [ctx+0x18] -> [frame+0x14]      0x734 [ctx+0x0c] -> [frame+0x1c]
```

`fpc_algo_end_enroll` (`0x5e4`) → `fpc_check_enrollment_allowance` (`0x5fe`) →

`fpc_db_trim_id_32` (`0xb2a`) → `frame+0x08` = id32.

### `get_finger_ids` (cmd 8)
`0x8ea fpc_db_get_indices(db, gid, &arr, 5, &count)`; valida `count <= +0x08`;
laço `fpc_db_get_fingerprint_id` + `fpc_db_trim_id_32` gravando u32 em `+0x0c+4i`;
`0xa6e str r0,[sp,#0x14]` → `+0x08` = count (o mesmo campo que entrou como capacidade).

## 4. `unknowns`

1. **Semântica** de `frame+0x14` e `frame+0x1c` na resposta do `identify` (mód. 11 cmd 4):
   são gravados a partir de `ctx+0x18` e `ctx+0x0c`, mas o HAL não os usa.
2. **Token de hw_auth**: significado do `u32 BE = 2` (bloco+0x19) e do `u64 BE` vindo de
   `S+0xa8` (bloco+0x1d), onde `S = *(ctx_mod3+0x00)`. `S+0xa8` é zerado para `ff..ff` por
   `fpc_match_result_reset` (cmd 1), mas quem o preenche depois não foi localizado.
3. **Criptografia do blob** (`fpc_wrap_crypto`/`fpc_unwrap_crypto`): as chamadas vão para
   *veneers* ARM (`0x90, 0x9c, 0xa8, 0xb4`) que saltam para uma tabela de syscalls do TEE
   **fora** da imagem reconstruída. Só o envelope é conhecido (`[0]` = tamanho plano,
   payload em `+0x34`).
4. **`fpc_ta_hw_auth_unwrap_key`**: idem (veneer `0xcc`); sabe-se o efeito (32 bytes em
   `ctx+0x65`) e a checagem do rótulo `keymaster64`.
5. **Quem chama o módulo 3 / cmd 3** em produção: o único emissor no HAL é
   `fpc_tee_authorize_enrol` (frame montado com `movi v0.2s,#3`), cuja origem no fluxo
   normal de enrol não foi rastreada até o topo.
6. **`get_identify_statistics` (11/18)**: existe no HAL, mas este TA rejeita `cmd > 11`.
   Não se sabe se é HAL mais novo que o TA ou código morto.
7. **`update_template` (11/5)**: o byte de resposta pode ser `0/1` (`0xad0` vs `0xa42`) ou o
   id32 truncado (`0x7b6`, compartilhado com o `identify`); os dois caminhos não ficaram
   separáveis com certeza.
8. **Valores iniciais** do `ctx` do módulo 3 (`0x2ce1f0`): `.bss` zerada no arquivo, e o
   vínculo `ctx+0x00 -> S` é feito em tempo de execução por uma rotina sem símbolo em
   `0x3d74` (`0x3d84 str r0,[r1]` com `r0 = fpc_bio_get_handle()`). No módulo 11 o slot
   `0x2cf07c` já vem inicializado no arquivo (`0x001188d8`), mas o objeto apontado cai em
   região zerada, então os campos dele também não são legíveis estaticamente.
9. Não foi feita validação dinâmica de nada disso: nenhuma amostra real de blob, token ou
   imagem foi comparada com a estrutura acima.
